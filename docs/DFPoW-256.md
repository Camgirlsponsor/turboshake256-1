# DFPoW-256

Dynamic Function Proof of Work, draft 0.1.

This draft is a research proof of work. It is a specification of a hash-like function and of the checks around it. It is not a claim that the inner function is a secure cryptographic hash, a password hash, a VDF, or an ASIC-proof puzzle. The test vectors at the end are part of the draft. `python/dfpow.py` is a reference implementation; an implementation that disagrees with those vectors disagrees with draft 0.1.

## Recommendation

Keep the part that makes the idea worth building.

A block carries an ordinary header. Mining is a search for a nonce. Consensus checks one inequality:

```text
DFPoW(epoch_seed, header) <= target(header.difficulty)
```

The nonce is not fed to one fixed compression function. It is fed to BLAKE3, and that digest is the seed of a small program. Nonce 1000 and nonce 1001 are different programs. The block stays small because the program is recomputed by every verifier. Difficulty stays a conventional 256-bit target. Pools, retargets, and heaviest-chain selection can sit outside the weird part.

That is the feature to build around: a machine generator feeding a machine, with a Bitcoin-shaped interface.

The changes below are what I would make before calling the first experimental version done. They are already reflected in this draft and in the reference implementation.

| Piece | Change I would make | Why |
| --- | --- | --- |
| Instruction stream | Each round runs a fixed ChaCha quarter-round, then one of the eight named operations, then one memory step. The eight operations are a permutation inside every group of eight rounds. | A free schedule includes all-XOR programs, even multipliers, and zero rotations. Those are shorter to evaluate than the program you meant to run, so miners hunt them and difficulty stops measuring work. A balanced accent list keeps the nonce-specific program and gives every nonce the same operation counts. |
| Rotations inside the quarter-round | Leave them at ChaCha's 16, 12, 8, 7. Let the seed choose a second rotation, in 1..31, for the accent only. | Randomizing the diffusion constants is how a generated ARX function becomes weak. The seed still chooses registers, the accent, the extra rotation, the multiplier, the constant, and the S-box. |
| S-box | Build it with a fixed-length Fisher-Yates shuffle so it is always a permutation. | A raw 256-byte table is not a permutation, and rejection sampling in parameter generation is a verification denial-of-service: the miner chooses the seed. |
| Multiplier | Force `m \| 0x80000001`, and mix both halves of the 64-bit product into the state. | An even multiplier destroys bits. The low half of an odd multiply is bijective but diffuses poorly; the high half is the part worth having. |
| Large memory | Split it. A 1 MiB dataset depends on an epoch seed and is shared, read-only, and non-seekable. A 2 KiB scratchpad is private to the nonce, writable, and fully committed at the end. | A 16–32 KiB pad derived from every nonce is generated by a seekable XOF, so a caller can recompute the few touched words, and the fill can cost as much as the function. Private writable memory is also paid once per parallel lane. The epoch dataset is paid once and reused. |
| Rounds | 256, not 64. The count is packed into the preimage. | 256 rounds is 32 repetitions of each accent and a serial address chain of length 256. Sixty-four rounds is enough to demonstrate the idea and short once the rest of the hash is real. Treat 256 as a draft constant, not a tuned one. |
| Finalizer | BLAKE3 over a fixed 208-byte preimage: domain, parameters, epoch, seed, final state, address, eight scratch words, eight dataset words. | "Selected scratchpad data" has to be exact, or two honest implementations fork. The finalizer is the output canonicalizer. It is not the source of mining difficulty. |
| Self-reference | One construction. The nonce is inside the seed, and the low and high halves of the nonce are xored into state words 0 and 1 before the program runs. | The generated function is applied to a state that already contains the nonce. A second mode, `F(seed, nonce)(seed \|\| nonce)`, would describe the same idea with two hashes to specify. |
| Difficulty | `target = 2^(256-d) - 1`. Success probability is exactly `2^(-d)`. Chain work of a block is `2^d`. | Summing the difficulty exponents treats a difficulty-30 block as 1.5 times a difficulty-20 block. It is 1024 times the expected work. |
| Binding | `chain_id` (16 bytes) and the parameter triple `(dataset_bytes, scratch_bytes, rounds)` go into every BLAKE3 preimage. | Two chains, or two parameter revisions, must not share work. Bumping a size without bumping a domain string is how that happens by accident. The parameters are inside the preimage, so the accident fails closed. |

What I would leave alone: the ordinary header, the external target check, BLAKE3 as the seed and the finalizer, an 8-operation vocabulary, a data-dependent address chain, regeneration of the program at verification time, and an explicit statement that this is not yet a security claim.

## Pipeline

```text
epoch_seed                          header prefix              nonce
    |                                      |                      |
    v                                      v                      v
BLAKE3 XOF                          BLAKE3 seed  <----------------+
    |                                      |
    v                                      v
forward mix + backward mix          3,551-byte program tape
    |                                      |
    v                                      v
1 MiB dataset  --------+            S-box, constants, accents
(shared, read-only)    |                   |
                       v                   v
                 2 KiB scratch      eight 32-bit words
                 (private)                 |
                       |                   |
                       +-------> 256 rounds
                                 quarter-round
                                 one accent
                                 dataset read + scratch update
                                         |
                                         v
                                 commit every scratch word
                                         |
                                         v
                                 BLAKE3 finalizer
                                         |
                                         v
                                   32-byte digest
                                         |
                              digest <= target ?
```

Across nonces the search is parallel. Inside one nonce the address chain is serial: round `r+1` does not know its dataset index until round `r` has finished. That is a proof of work, not a verifiable delay function. A VDF forbids the parallel search. This design depends on it.

## Normative specification

### Word size and encodings

- Arithmetic on state words is mod `2^32`.
- The only 64-bit product is the MUL accent. Only its low 32 bits and high 32 bits are kept.
- Multi-byte integers in preimages are little-endian.
- `rotl32(x, n)` rotates a 32-bit word left by `n mod 32`. A rotation of 0 returns `x`. In languages where a 32-bit shift by 32 is undefined, the `n == 0` case has to be special.
- The 32-byte digest is an integer with **byte 0 as the most significant byte**. Difficulty looks at the front of the hex string. This is the opposite of Bitcoin's internal byte order, on purpose, so a difficulty-8 digest begins with `00`.

`rotl32`:

```text
n = n mod 32
if n == 0: return x
return ((x << n) | (x >> (32 - n))) mod 2^32
```

### Constants

| Name | Value |
| --- | --- |
| Dataset | `2^20` bytes = 262,144 words |
| Scratchpad | `2^11` bytes = 512 words |
| Rounds | 256 |
| State | 8 words |
| Accents | 8, each used 32 times |
| Program tape | 3,551 bytes |
| Finalizer preimage | 208 bytes |
| Header | 84 bytes |
| Seed preimage | 160 bytes |

`PARAMS` is three little-endian uint32 values: `1048576`, `2048`, `256`.

Domain tags are 16 bytes, ASCII, NUL-padded:

| Tag | Bytes |
| --- | --- |
| `DFPW-SEED-v01` | seed |
| `DFPW-DATA-v01` | dataset |
| `DFPW-PROG-v01` | program tape |
| `DFPW-FINAL-v01` | finalizer |

BLAKE3 means the BLAKE3 specification: the 32-byte hash, and the extendable output function whenever this draft asks for more than 32 bytes. Domain separation is a fixed-width prefix. Keyed BLAKE3 and `derive_key` are not used.

`chain_id` is a 16-byte chain constant. `epoch_seed` is 32 bytes, chosen by the chain as specified later. Neither is a free field a miner can vary inside a block without the chain rules noticing: both are inputs to the hash, and the chain decides their legal values.

### Header

| Offset | Length | Type | Field |
| --- | --- | --- | --- |
| 0 | 4 | uint32 | version |
| 4 | 32 | bytes | previous block hash |
| 36 | 32 | bytes | Merkle root |
| 68 | 4 | uint32 | timestamp, Unix seconds |
| 72 | 4 | uint32 | difficulty `d` |
| 76 | 8 | uint64 | nonce |

The prefix is the first 76 bytes. The nonce is the last 8. Version here is the block version. The algorithm version lives in the domain tags and in `PARAMS`.

### Target

For an integer difficulty `d` in `0..256`:

```text
target(d) = 2^(256 - d) - 1
```

The header is valid for this draft's hash check when

```text
int_be(digest) <= target(d)
```

and `d` equals the difficulty the chain currently requires. A uniform digest meets the inequality with probability exactly `2^(-d)`.

| `d` | Target | Probability | How the hex looks |
| --- | --- | --- | --- |
| 0 | `2^256 - 1` | 1 | any digest |
| 8 | `2^248 - 1` | `2^-8` | first byte `00` |
| 20 | `2^236 - 1` | `2^-20`, about one in a million | five leading zero hex digits |
| 256 | 0 | `2^-256` | only the all-zero digest |

`d > 256` cannot appear in a valid header. There is no digest it would accept, and a verifier should reject it before doing any other work.

Block work is `2^d`, not `d`. Chain work is the sum of block work. A luckier digest does not increase the work of a block whose difficulty word is `d`.

The difficulty word is inside the prefix, so it is inside the seed. A share check reuses a digest against a **lower** bar. It does not rewrite the difficulty word. Rewriting it produces a different seed and a different program. The pool's header carries the network difficulty; the pool compares the digest with `target(share_difficulty)`.

### Seed

```text
seed = BLAKE3(
    DFPW-SEED-v01
 || chain_id
 || PARAMS
 || epoch_seed
 || prefix
 || nonce
)
```

That preimage is 16 + 16 + 12 + 32 + 76 + 8 = 160 bytes. Changing the nonce changes the seed. Under the usual assumption that BLAKE3 behaves like a random oracle, adjacent nonces produce independent seeds, and therefore independent programs.

### Dataset

The dataset depends on `chain_id`, `PARAMS`, and `epoch_seed`. It does not depend on the nonce or on the rest of the header. Miners and nodes cache it for the whole epoch.

```text
raw = BLAKE3-XOF(
    DFPW-DATA-v01 || chain_id || PARAMS || epoch_seed,
    2^20 bytes
)
```

Interpret `raw` as 262,144 little-endian words `x[i]`.

```text
w = le32(epoch_seed[0:4]) XOR le32(epoch_seed[4:8])
for i in 0 .. 262143:
    w = rotl32(w XOR x[i], 7) * 0x9E3779B9     mod 2^32
    dataset[i] = w
for i in 262142 .. 0:
    dataset[i] = dataset[i] XOR rotl32(dataset[i + 1], 5)
```

`0x9E3779B9` is odd, so the multiply is a bijection for a fixed `x[i]`. The forward pass makes word `i` depend on `x[0]..x[i]`. The backward pass makes word `i` depend on word `i+1`, and the last word depends on every `x[j]`. A finished word therefore depends on the entire XOF output. BLAKE3's extendable output is seekable; this mix is not. Computing any dataset word that a nonce actually touches requires the full buffer.

The dataset is read-only after construction. An implementation that writes it will fork.

### Program tape

```text
tape = BLAKE3-XOF(
    DFPW-PROG-v01 || chain_id || PARAMS || seed,
    3551 bytes
)
```

The tape is consumed in order, with no rejection sampling and no early exit. Parameter extraction is allowed to be slightly biased. It is not allowed to loop, because the miner chooses the seed and a loop would be a verifier denial of service.

**S-box, 255 bytes.** Start from `S = [0, 1, ..., 255]`. For `i` from 255 down to 1, read a byte `b` and swap `S[i]` with `S[b mod (i+1)]`. The result is always a permutation of `0..255`. It is not a uniform random permutation, and it is not an AES S-box. It is an accent, not the diffusion floor.

**Round records, 256 × 12 bytes.** For each round, in order:

| Field | Width | Rule |
| --- | --- | --- |
| constant `K` | uint32 | as read |
| rotation `R` | uint8 | `(b mod 31) + 1`, so `R` is in `1..31` |
| register bytes `b0, b1, b2` | 3 × uint8 | see below |
| multiplier `M` | uint32 | `word \| 0x80000001` |

`M` is odd and its high bit is set, so multiplication by `M` mod `2^32` is a bijection.

**Accents, 32 × 7 bytes.** For each group of eight rounds, start from `[0,1,2,3,4,5,6,7]` and run the same Fisher-Yates step for `i` from 7 down to 1. Each group is a permutation of the eight accents. Across the hash, each accent runs exactly 32 times. There is no cheaper program to go looking for.

Accent names, in numeric order: `XOR`, `ADD`, `ROT`, `MUL`, `SBOX`, `XORROT`, `ADDROT`, `MIX`.

**Registers.** In round `r` the pinned index is `p = r mod 8`. Build the ascending list of the other seven indices. Take the element at position `b0 mod 7` (positions start at 0), remove it, and shift the tail down. Repeat with `b1 mod 6` of what remains, then `b2 mod 5`. The quarter-round's `(a, b, c, d)` inputs are `(p, first removal, second, third)`. Four distinct words. Word `k` is the `a` input exactly 32 times per hash.

### Initial state and scratchpad

```text
W[i] = le32(seed[4*i : 4*i+4])    for i in 0..7
W[0] ^= le32(nonce[0:4])
W[1] ^= le32(nonce[4:8])
```

The program was derived from a seed that already contains the nonce. The state the program mixes also contains the nonce. That is the self-reference: the nonce selects the function, and the function is given the nonce.

```text
origin  = W[3] mod 262144
tumbler = W[5] | 1
for i in 0 .. 511:
    scratch[i] = dataset[(origin + i) mod 262144]
                 XOR rotl32(tumbler, i mod 32)
                 XOR i
```

This is a sequential window, not a second XOF. The following sweep is what makes every one of the 512 words visible to the digest, including words the random walk never revisits.

### One round

Set `addr = W[7]` before round 0. For round `r` from 0 through 255, let `(i0, i1, i2, i3)` be the registers selected above, and write `A, B, C, D` for `W[i0]..W[i3]`. Let `Keff = (K XOR r) mod 2^32`. The accent and the memory step see the words produced by the previous step. In the MIX row, `B` in the address update is the `B` just computed.

1. `A ^= Keff`.
2. ChaCha quarter-round on `(A, B, C, D)` with rotations 16, 12, 8, 7:

```text
A += B;  D ^= A;  D = rotl32(D, 16)
C += D;  B ^= C;  B = rotl32(B, 12)
A += B;  D ^= A;  D = rotl32(D,  8)
C += D;  B ^= C;  B = rotl32(B,  7)
```

3. Apply the accent named by this round's permutation. Additions are mod `2^32`.

| Id | Name | Effect |
| --- | --- | --- |
| 0 | XOR | `C ^= A XOR B`; `D ^= rotl32(C, R)` |
| 1 | ADD | `C = C + A + B`; `D ^= C` |
| 2 | ROT | `C = rotl32(A, R) XOR B`; `D ^= rotl32(C, 8)` |
| 3 | MUL | `prod = B * M` as a 64-bit product; `B = lo(prod)`; `C ^= lo(prod)`; `D ^= hi(prod)` |
| 4 | SBOX | `C ^= SboxWord(A)`; `D ^= SboxWord(B)` |
| 5 | XORROT | `C ^= A XOR rotl32(B, R)`; `D = D + C` |
| 6 | ADDROT | `C = A + rotl32(B, R)`; `D ^= rotl32(C, 8)` |
| 7 | MIX | `v = dataset[(addr + A + C) mod 262144]`; `A ^= v`; `B = B + v`; `C ^= rotl32(v, R)`; `D ^= v`; `addr = addr + v + B` |

`SboxWord` applies `S` independently to each byte of the word and reassembles them in little-endian byte order (low byte first).

4. Memory step, always, after the accent:

```text
v    = dataset[(addr + C) mod 262144]
sidx = (A XOR v) mod 512
s    = scratch[sidx]
B   ^= s
D    = D + v
scratch[sidx] = rotl32((s XOR A XOR Keff) + v, 5)
addr = B + rotl32(v XOR s, 3)
A   ^= rotl32(v, R)
```

`addr` is a full 32-bit word. It is reduced mod 262,144 only when it indexes the dataset. The next round's quarter-round reads the updated words, so the address chain is serial.

On the nonce-1000 vector the scratch fill reads a window of 512 dataset words, the rounds read 288 further dataset words (800 distinct before the finalizer), and the rounds read and write 201 distinct scratch words. Those counts are properties of that vector, not consensus minimums. The commitment below is what makes the unvisited scratch words count.

### Scratch commitment

After round 255:

```text
acc = addr
for i in 0 .. 511:
    acc = rotl32(acc + scratch[i], 5) XOR (i * 0x9E3779B9)     mod 2^32
for i in 0 .. 7:
    W[i] ^= rotl32(acc, 4*i + 1)
    acc = rotl32(acc XOR W[i], 3)
addr = acc
```

The rotations in the second loop are 1, 5, 9, 13, 17, 21, 25, 29. Every scratch word affects `acc`, and `acc` is mixed into every state word. A lazy implementation still has to materialize the whole pad before it can produce the digest.

### Finalizer

Build a 208-byte preimage:

| Offset | Length | Contents |
| --- | --- | --- |
| 0 | 16 | `DFPW-FINAL-v01` |
| 16 | 16 | `chain_id` |
| 32 | 12 | `PARAMS` |
| 44 | 32 | `epoch_seed` |
| 76 | 32 | `seed` |
| 108 | 32 | `W[0]..W[7]`, each uint32 |
| 140 | 4 | final `addr` |
| 144 | 32 | eight scratch words |
| 176 | 32 | eight dataset words |

Scratch sample `i` is `scratch[(W[i] + i * 0x9E3779B9) mod 512]`.

Dataset sample `i` is `dataset[(W[i] XOR addr XOR (i * 0x85EBCA6B)) mod 262144]`.

```text
digest = BLAKE3(preimage)
```

### Chain binding

The hash function takes `chain_id` and `epoch_seed` as inputs. The chain defines which values are legal.

Recommended rule, not a second hash mode:

- Pick a 16-byte `chain_id` at genesis and never change it without a hard fork.
- `EPOCH_LENGTH = 128` blocks.
- For `height < EPOCH_LENGTH`, `epoch_seed` is a published 32-byte genesis constant.
- Otherwise let `epoch_start = height - (height mod EPOCH_LENGTH)`. Set `epoch_seed` to the hash of block `epoch_start - 1`.

The dataset for an epoch is then known as soon as the last block of the previous epoch exists, and it stays valid for 128 blocks. A chain may use a different epoch length. A chain that sets `epoch_seed` from every block's parent hash is still implementing this hash; it has chosen to rebuild the dataset every block.

Separately, the chain must set `header.difficulty` to the retarget output for that height. The hash check does not do this. A miner who was free to write `d = 0` would produce a valid digest on the first nonce, worth `2^0` work. A miner who was free to write a huge `d` would be redefining the work accounting. Both are chain-validity rules.

Retarget itself should be an existing algorithm. ASERT (`aserti3-2d` is the usual reference) is a sound default. The ideal block interval and the ASERT time constant are chain parameters. This draft does not invent a retarget.

The 64-bit nonce is finite. The chain needs a coinbase extra-nonce so the Merkle root can change when a miner wants a fresh prefix. That is ordinary, and it matters more if a single job is ever hashed quickly enough to walk a large fraction of `2^64`.

Header validity also needs the usual contextual checks this draft does not define: parent exists, timestamp is inside the chain's window, Merkle root matches the transactions, `version` is one the chain understands.

## Mining and verification

Verification of one header:

```text
dataset = Dataset(chain_id, epoch_seed)          # cached for the epoch
digest  = Execute(dataset, chain_id, epoch_seed, header)
accept if header.difficulty == required(height)
      and int_be(digest) <= target(header.difficulty)
```

The miner does not send the program, the scratchpad, or the dataset. A missing cache is rebuilt. A wrong cache produces a digest the network rejects.

A miner caches the dataset and varies the nonce:

```text
dataset = Dataset(chain_id, epoch_seed)
for nonce in assigned_range:
    digest = Execute(dataset, chain_id, epoch_seed, header_with(nonce))
    if int_be(digest) <= target(share_or_block_difficulty):
        submit header
```

Allowed optimizations, all of which must return the same digest:

- Caching the dataset for `(chain_id, PARAMS, epoch_seed)`.
- Running many nonces at once, each with a private scratchpad and a private state.
- Computing the single selected accent, which is what a fast miner will do.

Computing all eight accents and selecting the result with arithmetic is equivalent and slower. It is a legal implementation. It is not a required one. Predicate execution is how a lockstep GPU would avoid divergent branches; the CPU miner will just switch.

Not equivalent, and not legal: skipping rounds, skipping the scratch commitment, sharing a scratchpad across nonces, writing the shared dataset, or treating a digest computed under a different difficulty word as if it belonged to this header.

## What the inner function is for

The final BLAKE3 makes the published digest avalanche even if the inner mixer is biased. The seed is inside the finalizer, and the seed changes with every nonce. A smoke check on the draft vectors shows the expected surface behavior: the digests of nonce 1000 and nonce 1001 differ in 121 of 256 bits. That check does **not** prove that the rounds do work. A constant inner function would still avalanche, because the seed would still change.

The rounds are work because the verifier recomputes them and the address chain has no known shortcut. The assumptions, stated so they can be attacked, are:

1. BLAKE3 is preimage-resistant and behaves like a random oracle on the domain-separated inputs above. Then digests are uniform, success probability is exactly `2^(-d)`, and distinct nonces yield independent programs.
2. For all but a negligible fraction of seeds, producing the final state, the final address, and the scratch sample is not substantially cheaper than running the 256-round chain, the scratch fill, and the scratch commitment.
3. The dataset mix has no shortcut that materializes the words a nonce needs without work comparable to building the dataset. The dataset is amortized across the epoch, so this cost is not charged to every nonce. A miner who skips it and guesses the words fails verification.

Assumption 2 is the one this draft does not prove. It is why the construction is a research PoW and not a primitive to put in a wallet.

What the structure does achieve, and what the reference tests lock:

- Every program is total: permutation S-box, odd multiplier, nonzero accent rotation, four distinct registers, fixed tape length, fixed round count.
- Every program has the same histogram: 32 of each accent, 256 quarter-rounds, 256 mandatory memory steps, one full scratch commitment.
- The quarter-round rotations cannot be weakened by the seed.
- On the nonce-1000 vector, flipping one bit of the eight-word state after nonce mixing and before the scratch fill changes the final state in 108 to 148 bits (mean 127.5 over 32 flips). That is a smoke check of inner diffusion on one input, not a proof.
- Flipping the dataset changes the digest. The dataset is not written by execution.

Shortcuts that were designed out, and the reason they had to be:

| Shortcut | What stops it |
| --- | --- |
| Ignore the program and submit `BLAKE3(header \|\| nonce)` | The finalizer commits to the post-execution state. A wrong state fails verification. |
| Prefer seeds whose program is all XOR, or whose multiplier is even | No seed has that program. The histogram and the multiplier mask are structural. |
| Seek the BLAKE3 XOF and compute only the dataset words that are read | Each finished word depends on the whole XOF output via the forward and backward mixes. |
| Skip initialisation of unread scratch words | The commitment sweep folds every scratch word into the state. |
| Make verification slow for a chosen nonce | Tape length, round count, and sweep length are fixed. There is no rejection loop. |
| Reuse work across chains or parameter sets | `chain_id` and `PARAMS` are in every preimage. |
| Reuse a share header at a different difficulty word | The difficulty word is in the prefix, hence in the seed. |
| Replay a block at another epoch | `epoch_seed` is in the seed, the dataset, and the finalizer. |

## Hardware, without the usual claim

The point of the generated program is that a SHA-256 ASIC is the wrong circuit. The circuit that *is* the right shape is still an ASIC, later, and this draft does not pretend otherwise.

A lane needs:

- a BLAKE3 (or a cached dataset plus a BLAKE3 of a 160-byte seed and a 3,551-byte tape),
- a decoder for the accent id,
- an 8-word datapath that can do the quarter-round, the eight accents, and a 32-bit multiply,
- 2 KiB of private scratch,
- random read access to the shared 1 MiB dataset.

None of that is exotic silicon. One mebibyte of shared SRAM is a normal macro. Two kibibytes times a few thousand lanes is the larger private-memory bill, and it is still an on-chip design. Data-dependent 32-bit addresses stop a designer from turning the dataset walk into a fixed access schedule known at tape-compile time, because the address is the output of the previous round. They do not stop a designer from building the lane.

So the progression this is aimed at is a real one, and it should be described as a datapath change rather than as resistance:

| Stage | What it implements |
| --- | --- |
| CPU | The reference algorithm. Dataset cached per epoch. Nonces are independent. |
| GPU | The dataset lives in device memory. Each lane has its own state and scratch. Accent dispatch is a switch or a predicate. Random dataset reads are uncoalesced. Two kibibytes of private scratch per lane is enough to limit occupancy; that is a tuning input for a GPU port, not a result this draft has measured. |
| FPGA | A small programmable round engine plus block RAM for the dataset. |
| ASIC | Seed generator, tape decoder, round datapath, per-lane scratch, shared dataset SRAM. |

Raising `DATASET_BYTES` until the dataset no longer fits in a cheap shared SRAM is the knob that moves the cost onto a memory bus. Raising `ROUNDS` is the knob that lengthens the serial chain if a compiled profile shows tape generation dominating the marginal nonce. Both are hard-fork changes: they alter `PARAMS`, which alters every digest. Draft 0.1 keeps the dataset at 1 MiB so a node can build it quickly and so the algorithm can be reimplemented without a memory-hard benchmark harness. That size will fit on a chip. Publishing a larger number before a compiled miner exists would only be a guess.

Floating point is excluded. Consensus software should not depend on rounding modes, and floating-point units are a poor way to express "we would like CPUs to have an advantage." Integer MUL is specified because it is exact.

## What I would measure before a testnet

The Python reference, CPython 3.12 and blake3 1.0.9, on the machine that produced the vectors:

| Action | Time |
| --- | --- |
| Build the 1 MiB dataset | 0.16 s |
| One nonce after the dataset exists | 1.5 ms |
| Difficulty-8 search in that interpreter | nonce 37 |

Almost all of the 1.5 ms is the Python round loop. BLAKE3 itself is native code in that process. These numbers are not hashrate, and they are not a reason to set `d`. A C or Rust miner is required before any parameter is treated as final. The profile that would justify a version bump is concrete:

- fraction of marginal nonce time spent in BLAKE3 tape expansion versus the serial memory chain,
- cycles per nonce and bytes of private state per lane,
- verification time for a node that has the epoch dataset cached, and for a node that does not,
- confirmation that operation counts do not vary across nonces (they should not; cache timing will).

If tape expansion is a large share of a compiled nonce, the follow-up is a fixed-width expander seeded by the 32-byte seed (ChaCha20 or xoshiro256\*\*), a domain tag of `v02`, and new vectors. It is not in this draft. One hash primitive is easier to implement twice, and two independent implementations should match these vectors before a third primitive is added.

Also before any public network:

- a second implementation, in another language, checked against the vectors,
- a wider inner-diffusion sample than the 32-flip smoke check,
- a decision, written down, that 1 MiB is either the launched size or the size that got replaced,
- chain rules for retarget, timestamp, and epoch seed reviewed as chain rules rather than as part of the hash.

### A valid difficulty-8 header

Same version, parent, Merkle root, and timestamp. Difficulty word is 8. Nonce is 37.

```text
digest  00a02a44532a21a5adc26d4a7041a0b7d28de0c222b55910f0c051fc34e3e978
```

The leading `00` is exactly difficulty 8: the next nibble is `a`, so the ninth bit from the top is 1, and difficulty 9 rejects this digest. Block work is `2^8 = 256`. The same nonce with the difficulty word set to 20 is a different hash and does not meet difficulty 20.

## Prior art, and the BAB64 cut

The shape borrows from work that already separated "parameterize a real core" from "invent a random machine":

- ChaCha's quarter-round is the diffusion floor, used as Bernstein specified the rotations, not as a suggestion to be re-rolled per nonce.
- Ethash showed the operational pattern this draft uses: a dataset that changes on an epoch, a nonce that only chooses the walk. RandomX showed the complementary piece: a private writable scratchpad next to a shared dataset, with addresses on a dependency chain.
- ProgPoW's useful lesson is the negative one. Randomizing the schedule of a core you already trust survives contact with implementers. An unconstrained ISA does not, because some of the "programs" are degenerate and the rest are a compatibility hazard.

BAB64, as you described it, derives an S-box, a rotation schedule, round constants, and an initial state from a 4,096-byte image, then runs that derived function over the image: 128 blocks, 32 rounds each, 4,096 round evaluations, a few kilobytes of working set. I have not re-measured that implementation. The cut you proposed is the one I would make. The image is an awkward carrier for what is really a parameter tape. A blockchain header does not want a 64×64 frame. It wants a nonce, a seed, and a function of that seed.

DFPoW-256 is that cut, plus the constraints in the table at the top. The generated program stays. The requirement that every generated program be a complete, equal-cost instance of one mixer is the part BAB64-style parameter derivation has to add before the result is a consensus function rather than a family of functions of unequal strength.

## Open problems

- There is no reduction showing that computing the inner state is as hard as running it. A shortcut that works for a noticeable fraction of seeds breaks the work accounting even though the finalizer still looks uniform.
- The S-box is a seed-derived permutation with a biased shuffle. Its differential uniformity is unanalyzed. It is not allowed to be the only nonlinearity. The quarter-round and the finalizer are the floor.
- Cache timing depends on addresses. Operation counts do not. A constant-time hardware lane and a cache-sensitive CPU will not take the same number of cycles, and that is ordinary. A difference in *instruction* counts between nonces would not be ordinary; the draft forbids it.
- 1 MiB and 256 rounds are draft sizes. Change them by changing the version, not by silent agreement.
- Nothing here is a password hash, a key derivation function, a signature hash, or a delay function. The parallel nonce search is the mining model. The serial chain is only inside one attempt.
